# Existing Session Batch Participant Append Design
日期：2026-04-22

## 1. 背景

项目已经支持：
- 在创建会话时配置多个参与者
- 在会话详情页追加单个已认证模型

当前缺口是：
- 现有会话里一次只能加一个模型
- 用户如果想把一组新认证好的模型一起加进当前会话，需要重复打开表单、重复提交

这会让“补齐一个团队”这种常见操作变得很慢，例如一次加入 `claude + codex + deepseek + kimi`。

## 2. 目标

1. 支持在现有 `active` 会话里一次追加多个参与者。
2. 保留当前 provider/model 下拉与认证体系，不新增自由填写模型名的路径。
3. 保持“新参与者从下一轮开始参与”的规则，不插入当前正在生成的轮次。
4. 普通会话与 `code_workspace` 都支持。
5. 失败时避免“部分成功、部分失败”带来的不一致体验。

## 3. 非目标

1. 本次不做已有参与者的批量编辑或删除。
2. 本次不做拖拽排序。
3. 本次不做生成中的热插入。
4. 本次不把单个追加接口删除，保留兼容。

## 4. 方案对比

### 方案 A：前端循环调用单个追加接口

优点：
- 后端改动最小

缺点：
- 会出现多次刷新、多次 toast
- 如果中间某一次失败，会出现部分追加成功
- 前端要自行处理回滚或错误恢复，复杂度反而更高

### 方案 B：新增批量追加接口

优点：
- 一次请求完成整体校验与整体写入
- 更容易保证原子性
- 前端交互更自然，用户点一次提交即可

缺点：
- 后端需要新增批量 API 和批量校验逻辑

### 结论

采用方案 B。

## 5. 设计决策

### 5.1 后端接口

保留现有：
- `POST /api/sessions/{session_id}/participants`

新增：
- `POST /api/sessions/{session_id}/participants/batch`

请求体：

```json
{
  "participants": [
    {
      "model_ref": "gpt-5.4",
      "provider_id": "provider-openai",
      "custom_id": "Reviewer",
      "role_desc": "review code"
    }
  ]
}
```

返回值仍然使用 `SessionDetail`。

### 5.2 原子性

批量追加必须是原子的：
- 任何一条参与者配置不合法，整批失败
- 不允许前几条成功、后几条失败

### 5.3 校验规则

复用现有单条追加规则，并扩展为整批校验：
- 会话必须是 `active`
- 会话不能处于 `is_generating`
- 总参与者数量不能超过上限
- 批次内部 `custom_id` 不能重复
- 不能与现有会话参与者 `custom_id` 冲突
- `model_ref`、`provider_id` 仍走既有校验逻辑

### 5.4 前端交互

会话详情页“Add participant”面板改为“批量草稿列表”：
- 默认展示 1 行草稿
- 用户可继续新增行
- 每行可独立选择 provider/model、alias、role
- 可删除未提交的草稿行
- 单次提交把所有草稿一起发给批量接口

### 5.5 兼容性

- 现有单个追加接口保留，避免影响已写好的测试和潜在外部调用
- 新 UI 直接走批量接口，即使只有 1 行也走批量路径

## 6. 数据流

1. 用户打开会话详情页的追加面板
2. 前端维护一个 `ParticipantConfig[]` 草稿数组
3. 用户填写多行后点击一次提交
4. 前端调用 `POST /api/sessions/{id}/participants/batch`
5. 后端在单个事务中完成校验和写入
6. 后端返回最新 `SessionDetail`
7. 前端用返回值刷新当前会话并清空草稿

## 7. 风险

1. 前端批量表单状态处理会比单行略复杂
2. 如果批量接口与单条接口逻辑分叉，后续容易漂移

对应控制：
- 后端把单条和批量都收敛到同一套内部写入方法
- 前端尽量复用创建会话页的参与者编辑控件思路

## 8. 验收标准

1. 会话详情页可一次添加多个模型。
2. 批量提交成功后，新增 alias 会立即显示在当前会话参与者标签中。
3. 任一条配置非法时，整批不写入。
4. `code_workspace` 模式下也可批量追加。
5. 相关前后端回归测试通过。
